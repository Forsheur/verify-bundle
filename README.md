# verify-bundle

`verify_bundle.py` checks a Forsheur evidence bundle — offline, on the Python 3
standard library alone, with nothing to install and no network access of any
kind. It is the reference implementation of those checks: no other tool
re-implements them, and the one that quotes it ([edit-report]) deliberately
refuses to.

```
python3 verify_bundle.py /path/to/forsheur-evidence-XXXX
```

**Download:** [latest release](https://github.com/Forsheur/verify-bundle/releases/latest)
— one file, plus `SHA256SUMS`. There is no build step and nothing to compile.

---

## Why this is published separately

The script already ships **inside** every bundle. Publishing it here changes
nothing about who can read it, and everything about who can check it.

A verifier that arrives inside the archive it vouches for is circular. Whoever
supplied the bundle supplied the script, and could have supplied one that
prints `VERDICT: PASS` over anything. Nothing inside the ZIP can settle that.

So settle it from outside. Every bundle's `README.txt` and `manifest.json` name
the version and SHA-256 of the copy they carry, and the report produced by
[edit-report] names the SHA-256 of the copy that actually ran. Compare either
one against a release here:

```sh
shasum -a 256 verify_bundle.py              # macOS, Linux
certutil -hash-file verify_bundle.py SHA256 # Windows
```

Three outcomes, and only one of them is interesting:

| What you find | What it means |
|---|---|
| Matches the release named by the bundle's `version` | The expected case. |
| Matches an **older** release | Also ordinary. Bundles are generated by the server that existed at the time and keep the verifier they shipped with. Not a finding. |
| Matches **no** published release | Worth acting on. Run a copy from here against the bundle's data before believing anything the bundled copy printed. |

A Forsheur server also publishes its own embedded copy at `/verifier`, with
`/verifier.sha256` and `/verifier.json`. That is a second copy, not an
independent one — it comes from the same party — which is exactly why this
repository exists as a third.

**What this does not fix.** The notary's public keys still ship in the bundle
and are cross-checked against a Forsheur-hosted
`/.well-known/forsheur-notary-keys.json`. Publishing the code does not move
that anchor. The residual trust sits on the keys, not on the verifier.

## What it verifies

Six links, each one refusing to stand on the one before it:

1. `sha256(payload.bin) == h_received` — the hash the capturing device signed.
2. `sha256(H_env ‖ H_received) == H_chunk` — the commitment the notary sealed.
3. The device signature over `H_chunk`, with the public key read from the
   envelope. Ed25519 for chunk format v2, ECDSA P-256 for v3 — the key's width
   says which, and **both are implemented here in pure Python**, so there is
   nothing to `pip install` before a signature can be checked.
4. Leaf → Merkle path → `merkle_root` → `block_hash`, then the notary's Ed25519
   signature over that block.
5. The hash-chain segment: every block links `prev → next` up to the cover
   block.
6. The cover block's Bitcoin anchor (`.ots`), at whichever of three levels your
   machine supports (below).

Where a bundle carries a manufacturer attestation chain, it also walks that
chain to Apple or Google. **Validity is evaluated at the instant the notary
sealed the bytes**, never at the moment you run this: certificates expire, and
a recording does not become false because a certificate aged.

## What it does not tell you

It establishes that these bytes are the bytes a particular device signed and a
notary sealed at a particular time. It says nothing about whether what was
filmed is true, nothing about what was out of shot, and nothing about who holds
the account — the chain ends at a public key, which is a pseudonym.

See [SECURITY.md](SECURITY.md).

---

## The Bitcoin anchor, three levels

The script degrades honestly rather than failing:

1. **`ots verify` installed and your own Bitcoin node** — fully trustless.
2. **Neither** — the built-in `.ots` parser reports the Bitcoin block height.
   Cross-check that block's timestamp on any explorer you like.
3. **Nothing at all** — the seal, the signatures and the chain are still fully
   verified. Only the anchor goes unexamined, and the report says so.

A missing capability is reported as a missing capability. It never becomes a
verdict about the recording.

## Usage

```sh
python3 verify_bundle.py <bundle.zip | extracted-directory>
python3 verify_bundle.py <bundle> --extract          # also write media streams
python3 verify_bundle.py <bundle> --json out.json    # machine-readable summary
python3 verify_bundle.py --version
```

**Windows:** unpack the ZIP and double-click `verify_bundle.cmd`. It finds
Python, offers a short menu, and keeps the window open. `verify_bundle.ps1` is
included for people who prefer PowerShell, but do not start with it: Windows
blocks downloaded PowerShell scripts under the default execution policy, and
batch files are not subject to it. Neither launcher contains any cryptography;
a bug in one can fail to launch, never forge a pass.

### Encrypted sessions

If the session is end-to-end encrypted the payloads are ciphertext, and
provenance is still proven without revealing content. A recipient granted
access at recording time can decrypt offline:

```sh
python3 verify_bundle.py <bundle> --extract --id-priv   # X25519 identity key
python3 verify_bundle.py <bundle> --extract --dek       # the raw 32-byte DEK
```

Both prompt with hidden input — a key never appears on the command line or in
your shell history. Decryption is checked against the device-signed plaintext
hash, so a wrong key fails loudly instead of yielding plausible garbage.

These two paths, and only these two, need `cryptography` and `pynacl`. Every
verification above runs without them.

### Attestation roots

Apple's and Google's published roots are pinned **inside the script**, with the
URLs they came from in the comments beside them. A root arriving inside the
archive being checked anchors nothing and is never read. If you would rather
not take this script's word for what Google publishes:

```sh
python3 verify_bundle.py <bundle> --attest-root google-root.pem
```

Walking the chain needs the `cryptography` package. Without it every other
verdict is unchanged and only the manufacturer link goes unexamined.

## The `--json` contract

`--json` writes `forsheur-verify-bundle/1`: the same checks the human text
shows, in the same order, from the same call sites. It carries no judgement the
text does not. It exists so a program can quote this script without parsing
English prose — a summary recovered by matching sentences is a dependency on
wording nobody versions.

The `verifier` object names the `path`, `sha256` and `version` of the copy that
ran, which is what makes the comparison at the top of this file possible.

## Relationship to the rest

- **This repository** verifies that a bundle is what a device signed and a
  notary sealed.
- **[edit-report]** takes a bundle *and a video that claims to come from it*,
  and describes where the two correspond and where they do not. It runs this
  script as a subprocess and quotes it verbatim; it contains no second
  implementation of these checks, on purpose — two implementations of one
  verification chain are two things that can be wrong, and the day they
  disagree neither is believable.

This repository is a **mirror**. The file is compiled into the Forsheur server
(`include_str!`) so that what a bundle contains and what the server publishes
are the same bytes by construction. Releases here are cut from that copy by
`sync.sh`; patches are welcome as issues or PRs and are applied upstream first.

## Reporting a problem

Open an issue for anything that is not itself a vulnerability. For a
vulnerability — in particular, any way to make this script print `PASS` over
material it should not — contact **security@forsheur.com** privately first, or
use the repository's private vulnerability reporting.

A report saying "this script accepted a bundle it should have rejected" is the
most serious kind there is here. So is the opposite.
